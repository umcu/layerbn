## A. Layers

### A1. Layer names and which variables are in each — **cells 7 + 17 + 26**

**This is the one that is not actually in the notebook.** It is loaded from a
data artefact:

```python
# cell 7
bn_vars = pd.read_parquet(DATA_DIR / 'bn_vars.parquet', engine='pyarrow')

# cell 17 — patch DROPOUT REASON into the dropout layer
bn_vars.loc[bn_vars['VARIABLE NAME'] == 'DROPOUT REASON', 'LAYER'] = 'L9 – Dropout'

# cell 26 — the layer map the whole analysis is constrained by
layer_map = bn_vars.groupby('LAYER')['VARIABLE NAME'].apply(list).to_dict()
```

So the expert layering — arguably *the* central scientific choice in the whole
pipeline — currently lives in `bn_vars.parquet`, which is generated by
`00_preprocess.ipynb` from `HBC_CODEBOOK_LABELS.xlsx` plus the hardcoded
`EXTRA_LAYER_ROWS` list. It is not visible or reviewable from the analysis
notebook, and it is not in git (`*.parquet` is gitignored).

Moving it into `spec.yml` is the single biggest gain here: it makes the
layering reviewable, diffable and citable.

**Blocker:** I cannot read `bn_vars.parquet`, so I cannot transcribe the exact
membership. See "What I need from you" at the end.

The cell 17 patch also disappears into the spec — assigning `DROPOUT REASON`
to `L9 – Dropout` becomes a line in the layer list rather than a post-hoc
`.loc[]` fix-up applied to a dataframe.

### A2. Layer **order** — **cell 26 (implicitly) and cell 28**

```python
layer_keys = list(layer_map.keys())  # "use list, not sorted, to preserve domain-defined order"
```

The comment says the order is domain-defined. It isn't. `pandas.groupby`
defaults to `sort=True`, so `layer_map`'s keys come out **alphabetically
sorted**, and `layer_keys` inherits that. It currently produces the intended
order only because the `L0…L9` prefixes happen to sort correctly.

This matters because layer order *is* the arc constraint — `build_bn` only
allows arcs from an earlier layer to the same or a later layer. A cohort whose
layers are named `Demographics`, `Imaging`, `Outcomes`, `Risk factors` would
get a silently wrong causal ordering (alphabetical: Demographics → Imaging →
Outcomes → Risk factors, putting outcomes upstream of risk factors).

In the spec the order becomes explicit: the sequence of the `layers:` list,
nothing else.

### A3. Layer display order for node colours — **cells 32 and 68**

Two different hardcoded lists:

- **cell 32** — 9 layers, used for `bn_joint`. Omits `L3 – Specialized biomarkers`.
- **cell 68** — 10 layers, used for `bn_with_biomarkers`. Inserts `L3 – Specialized biomarkers`.

Both then compute the same colour ramp (`min 0.111111`, `max 0.99999`,
`len-1` steps) and the same fallback (`0.5`).

These look like a duplicate of A2 with a rendering purpose, and my first
instinct was to derive the colour ramp from the spec's layer list. **That
would have changed every figure.**

The actual `layer_map` has **8** layers. Neither `L1 – Modifiable
demograhpics / Lifestyle factors` (cell 32) nor `L3 – Specialized biomarkers`
(cell 68) exists in it — both are phantom entries that survive only because
the lookup is `layer_color_map.get(layer_name, 0.5)`. But they still occupy
slots in the ramp: cell 32 divides the interval into 9 steps, cell 68 into 10,
where the real layers would give 8. Deriving the ramp from the spec would
shift the colour of every node in the published figures.

So cells 32 and 68 stay exactly as they are. This is consistent with §H
(rendering is out of scope) but for a sharper reason: these two lists are not
the layer order, they are a hand-tuned colour assignment that happens to be
written in the same shape.

## What could not be expressed, and will stay in code

Recorded here now; confirmed in the final report.

1. **`build_bn_biomarkers` (cell 61)** — the ablation variant applies the layer
   constraints but omits the post-learn outcome→dropout arcs that
   `core.build_bn` forces in. No spec value selects that; it needs either a
   `core.build_bn` parameter or the local function. Staying local.
2. **Alluvial plots and the dropout composition chart (cells 9–14)** — ~330
   lines of bespoke matplotlib keyed to T0/T2/T4 and Dutch dropout categories,
   reading a fourth artefact (`df_outcome_states.parquet`).
3. **Biomarker logistic regression (cell 64)** — statsmodels, a different
   method; picks its variables from `layer_map['L4 …']`, so it follows the
   spec's layers, but the model itself is code.
4. **The stroke-history blank fill (cell 8)** — `'STROKE HISTORY'` / `'CVA'`
   blanks → `'No'` / `'Nee'`. This is preprocessing that leaked into the
   analysis notebook; it belongs in `00_preprocess.ipynb`, which is out of
   scope here.
5. **MI/CMI cells** — the *targets* go in the spec, but the seven cells' print
   formatting and the choice of `bn_joint` vs `bn_with_biomarkers` per cell
   stay as code.
